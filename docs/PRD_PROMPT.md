> 이 문서는 **PRD 자체가 아니라**, Claude Code에 입력하면 `docs/PRD.md`(MVP PRD 문서)를
> 자동 생성하도록 설계된 **메타 프롬프트**입니다.
>
> **사용법**: 아래 `## 🎯 프롬프트` 섹션 전체를 복사해 Claude Code에 붙여넣으세요.
> 변수(`{{...}}`)는 채우거나, 비워두면 Claude가 합리적 기본값을 가정하고 가정 내역을 PRD 상단에 명시합니다.

## 🧩 제품 한 줄 요약

> **Notion에 입력한 견적서 내용을, 클라이언트가 별도 로그인 없이 웹 링크로 열람하고 PDF로 다운로드하는 서비스.**

- **입력(관리자)**: Notion 데이터베이스에 견적서 1건 = 1개 페이지로 작성
- **출력(클라이언트)**: 발급된 고유 URL 접속 → 웹에서 견적서 확인 → "PDF 다운로드" 클릭
- **MVP 범위**: 인증/결제/전자서명 등은 제외. "Notion → 웹 렌더링 → PDF" 단일 흐름에 집중.

## 🎯 프롬프트

```text
당신은 시니어 프로덕트 매니저이자 풀스택 아키텍트입니다.
아래 [제품 컨셉]과 [기술 제약]을 바탕으로 실행 가능한 MVP PRD 문서를 작성하세요.

# 출력 규칙
- 출력 파일: docs/PRD.md (한국어로 작성, 코드 식별자/변수명만 영어)
- 문서 톤: 엔지니어가 그대로 구현에 착수할 수 있을 만큼 구체적이고 검증 가능하게.
- 모호한 요구사항은 "추측"하지 말고, 합리적 기본값을 택한 뒤 [가정 및 의사결정] 섹션에 근거와 함께 명시.
- 모든 기능 요구사항은 측정 가능한 인수 기준(Acceptance Criteria)을 동반할 것.
- 범위를 벗어나는 아이디어는 [Out of Scope] 또는 [향후 로드맵]으로 분리.

# 제품 컨셉
- 핵심 가치: Notion에 입력한 견적서를 클라이언트가 웹으로 확인하고 PDF로 다운로드.
- 1차 사용자(Admin): 견적서를 Notion DB에 작성/수정하는 내부 담당자.
- 2차 사용자(Client): 발급된 링크로 견적서를 열람·다운로드하는 외부 고객. (로그인 없음)
- 데이터 원천(Single Source of Truth): Notion Database. 웹은 읽기 전용 렌더러.
- 대상 산업/통화/언어: {{대상_도메인 예: B2B SaaS, KRW, 한국어}}

# 기술 제약 (이 프로젝트 고정 스택 — 변경 금지)
- Framework: Next.js 15.5.3 (App Router + Turbopack), React 19, TypeScript 5
- Styling: TailwindCSS v4 + shadcn/ui (new-york)
- Forms/Validation: React Hook Form + Zod (필요 시)
- 데이터 연동: Notion 공식 API (@notionhq/client) 사용 가정
- PDF 생성 방식은 후보를 비교(예: @react-pdf/renderer 서버 생성 vs. Puppeteer/Playwright 서버 렌더 vs. 브라우저 print-to-PDF)하고 MVP 권장안 1개를 근거와 함께 선택
- 배포 환경: {{배포_타깃 예: Vercel}} 기준의 제약(서버리스 실행시간/메모리, 한글 폰트 임베딩 등)을 고려
- 아키텍처 원칙(CLAUDE.md 준수): 관심사 분리, DTO 패턴으로 Notion 응답 → 도메인 모델 매핑, 의존성 주입 지향, 핵심 로직 try-catch 에러 핸들링, 일관된 API 응답 구조(status/message/data)

# Notion 데이터 모델링 요구
- 견적서 1건을 표현하기 위한 Notion Database 속성(Property) 스키마를 제안:
  - 견적서 메타(견적번호, 발행일, 유효기한, 발신자/수신자 정보, 통화, 상태)
  - 항목 리스트(품목명, 설명, 수량, 단가, 금액)를 Notion에서 어떻게 표현할지(별도 DB 관계형 vs. 페이지 본문 블록 vs. JSON) 비교 후 MVP 권장안 선택
  - 합계/세금/할인 계산을 Notion에서 할지 웹에서 할지 결정하고 근거 명시
- Notion API 응답을 앱 내부 도메인 타입(InvoiceDTO 등)으로 변환하는 매핑 전략 기술

# 반드시 포함할 PRD 섹션 (이 순서대로)
1. 문서 개요 — 목적, 배경, 용어 정의(견적서/Invoice/Quote 구분 명확화)
2. 목표와 비목표 — MVP에서 달성할 것 / 명시적으로 안 할 것
3. 핵심 사용자 & 사용자 시나리오 — Admin/Client 각각의 User Story (As a ~, I want ~, so that ~)
4. 사용자 플로우 — Admin(Notion 작성→발급) / Client(링크 접속→열람→PDF) 단계별, 텍스트 다이어그램 포함
5. 기능 요구사항 — 기능별 ID(F-01...), 설명, 우선순위(MoSCoW), 인수 기준
6. 정보 구조 & 화면 정의 — 라우트 설계(예: /invoice/[id]), 각 화면의 구성 요소와 상태(로딩/에러/만료/Not Found)
7. 데이터 모델 — Notion DB 스키마 + 앱 도메인 타입(InvoiceDTO, LineItemDTO 등 TypeScript 인터페이스 예시)
8. 시스템 아키텍처 — 데이터 흐름도(Notion API → Next.js 서버 → 렌더/캐시 → 클라이언트), 캐싱/재검증(ISR/revalidate) 전략
9. PDF 다운로드 설계 — 생성 방식 비교표와 선택 근거, 한글 폰트/페이지네이션/파일명 규칙, 웹 화면과 PDF 레이아웃 일치 전략
10. 비기능 요구사항 — 성능(목표 LCP/PDF 생성 시간), 보안(링크 추측 방지·noindex·만료), 접근성, 반응형
11. 보안 & 접근 제어 — 인증 없는 공개 링크의 위험과 완화책(추측 불가능한 ID, 만료, 상태 기반 접근 차단)
12. 에러 처리 & 엣지 케이스 — Notion 미연동/삭제된 견적서/만료/네트워크 실패/대용량 항목
13. 성공 지표(KPI) — MVP 검증용 측정 가능 지표(열람율, PDF 다운로드 성공률, 페이지 로드 시간 등)
14. 마일스톤 & 범위 — MVP 작업을 검증 가능한 단위로 분해(WBS), 의존성 표시
15. Out of Scope & 향후 로드맵 — 인증, 결제, 다국어, 전자서명, 견적서 버전관리 등
16. 가정 및 의사결정 — 빈 변수에 대해 채택한 기본값과 근거, 미해결 질문(Open Questions)

# 분량 & 형식
```
